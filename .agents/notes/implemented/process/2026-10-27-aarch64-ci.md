# Agent Note: 增加原生 aarch64 CI 验证

Status: implemented

## 问题

本地已在 Kunpeng-920 aarch64 服务器完成 release 构建和完整测试，但 GitHub
Actions 的既有四门禁只在 x86_64 上运行。后续改动即便引入 x86-only 假设，也不会
在 PR 阶段被发现，ARM 适配会退化为一次性人工验证。

## 决策

在同一个 CI workflow 中增加一个轻量 `check-aarch64` job，使用 GitHub 公共仓库
提供的原生 `ubuntu-24.04-arm` runner，执行：

- `cargo build --release --locked`
- `cargo test --lib --tests --locked`

不重复 x86 job 的 fmt/clippy/doc 四门禁，也不引入交叉编译或自托管 runner，保持
项目原有的轻量 CI 定位。

## 备选方案

- **只在 x86 runner 上 `cargo check --target aarch64-unknown-linux-gnu`** — 能检查
  Rust 类型和部分代码，但不执行 aarch64 运行时，也不覆盖测试行为；否决。
- **把 fmt/clippy/test/doc 全部做 x86/aarch64 双矩阵** — 覆盖最完整，但重复昂贵且
  违背“轻量 CI”取向；否决。
- **自托管 aarch64 runner** — 可控制环境，但需要长期运维和凭据，不适合业余项目；
  否决。
- **只保留手工 ARM 验证** — 成本最低，但没有回归门禁；否决。

## 后果

- 公共仓库每次 push/PR 增加一个 4 vCPU ARM job；私有镜像需要自行提供 arm64
  runner 或调整标签。
- ARM job 只验证构建和运行时测试，不替代本地四门禁；x86 job 仍承担格式、lint、
  文档和 MSRV 检查。
- 本机已验证同一套 `cargo build` / `cargo test` 在 aarch64 上通过；新增 workflow
  job 尚未在 GitHub Actions 上实际执行，合并后需观察首个运行结果。

## 验证

- 本机 aarch64：`cargo build --release --locked`、`cargo test --lib --tests --locked`
  通过；release smoke compress/verify 通过。
- 新增 job 使用公开文档确认的 `ubuntu-24.04-arm` 标签；未在本地伪造 GitHub
  runner 运行结果。
