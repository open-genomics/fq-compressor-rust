# Agent Note: .fqc 归档采用自定义块索引二进制格式

Status: implemented

## 问题

FASTQ 压缩工具需要一个归档格式承载压缩数据。需求包括：按范围解压（随机访问）、并行压缩/解压、单块完整性校验、流式兼容，且 CLI 以单二进制分发、无运行时依赖。简单拼接的压缩流无法满足前三项。

## 决定

`.fqc` 归档为自定义二进制格式：`[magic][global header][block 0..N][reorder map(可选)][block index][footer]`。块索引位于文件末尾，每条 `IndexEntry` 记录 `{offset, compressed_size, archive_id_start, read_count}`，支持按读段区间二分定位目标块，无需扫描全文件。块独立压缩/解压/校验；streaming 与 archive 两种写入模式产出同一格式。格式细节以 `docs/reference/format-spec.md` 为准。

出处：原 `docs/architecture/decisions/001-block-indexed-format.md`（ADR-001，已采纳），2026-09-27 折叠进本树。

## 备选方案

- **简单拼接压缩流** — 最强论据：实现最简单、零格式开销；否决理由：无随机访问、无法并行、无法做部分验证，三项都是硬需求。
- **SQLite 存储** — 最强论据：成熟查询能力、事务、工具生态；否决理由：引入外部依赖破坏单二进制分发，文件头开销大，且与流式处理、生物信息学工作流不匹配。
- **HDF5 存储** — 最强论据：层次化组织、科学计算社区熟悉、原生分块压缩；否决理由：C 库依赖与格式复杂度对命令行工具过重。

## 后果

- **收益**：`fqc info`/`verify`/`--range` 解压可直接基于归档结构操作；多线程压缩解压有天然并行单元；单块损坏不影响其余块校验。
- **代价与已知上限**：格式实现复杂度高于拼接方案，每块有固定头部开销；格式演进靠版本字段预留空间，兼容性维护是持续成本。块大小是随机访问粒度与索引开销的权衡点——若典型使用形态变化（如极小范围查询成为主路径），重访默认块大小。
