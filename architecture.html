高性能架构设计

单二进制 Rust CLI，清晰分层的模块，块 = 独立并行单元：既支撑 O(log N) 随机访问，也支撑多块并行压缩/解压。三种执行模式在不产生格式碎片的前提下提供内存-吞吐量的灵活权衡。

1 分层架构

层次关键文件职责
CLIsrc/main.rs, src/commands/*解析参数、分发命令（compress / decompress / info / verify）
FASTQ I/Osrc/fastq/parser.rs, src/io/*FASTQ 解析、压缩流变体、原子输出
归档格式src/archive/format.rs, writer.rs, reader.rs编码 / 解码 .fqc 容器，块索引与校验
算法src/algo/*序列（ABC/Zstd）、质量（SCM）、ID、重排、双端
编排引擎src/engine/compression_engine.rs规范化请求、路由执行模式、捕获结果
流水线src/pipeline/*读取器 / 压缩器 / 写入器并行流（Pipeline 模式）
共享src/types.rs, src/error.rs, src/memory_budget.rs公共类型、退出码映射、内存预算估计

依赖方向单一：CLI → 编排 →（I/O、算法、格式）→ 流水线。算法与格式通过 CompressorTrait 解耦，块压缩器按读长类别与配置选择具体实现。

2 块索引：并行与随机访问的同一个答案

块是这个架构最关键的结构决定：每个块是独立压缩的读段子集，块之间零共享状态。这一个决定同时带来四项能力：

独立压缩单元：块间无交叉引用 → 天然可并行（多核压缩/解压） O(log N) 随机访问：尾部索引二分定位目标块 范围查询：只解压覆盖目标范围的块（--range） 按块验证：info / verify --quick 基于归档结构操作，不必全量解码 内存可控：块即内存上限的自然粒度，配合预算估计

这也是压缩比与随机访问张力的解法：块太小 → 索引开销大、ABC 无足够相似读段；块太大 → 随机访问粒度粗、内存峰值高。块大小（推荐值）即这个权衡的显式参数。

3 三种执行模式：内存 · 吞吐 · 压缩比的权衡

fqc 通过 CompressionEngine 路由到三种执行模式。关键约束：所有模式产出同一 .fqc 格式——因此模式选择是运维决策而非格式承诺，可随时切换。

模式标志内存重排压缩比适用场景
Archive（默认）全量摄入（高）启用最佳生产归档、长期存储
Streaming--streaming有界（低）禁用良好超大文件、内存受限
Pipeline--pipeline分阶段（中）禁用良好多核高吞吐生产流程
Archive 全量读取 → 全局分析（长度分类 + 相似性分组）→ 可选重排 → 压缩 Streaming 单遍增量读取 → 流式压缩（禁用重排）→ 增量写块 Pipeline reader →[块缓冲]→ compressor →[块缓冲]→ writer（三线程并发）

Archive 模式为最佳压缩比做全局分析（含 minimizer 重排）；Streaming 是严格低内存的单遍路径；Pipeline 用生产者-消费者三阶段在途缓冲最大化多核吞吐——三者共享同一解析器、算法与格式层。

4 内存预算：有界的资源承诺

--memory-limit 是全局参数，对 compress / decompress / verify 均生效。0 表示自动有限预算（约可用内存 75%，带硬性结构上限），并非无限内存。

  • 压缩：archive 与 pipeline 摄入时按该预算估计峰值，超限会在创建 .fqc 前失败并提示改用 --streaming（fail-fast，不留半成品）。
  • 解压 / 校验：按 operation 作用域预算约束声明与 zstd 分配，读取每个 header 前先校验大小再分配（src/memory_budget.rs）。
  • 代价提示：pipeline 仍是分段执行路径，不是严格低内存摄入——要严格低内存请用 --streaming。
# 1 GiB 有界压缩（流式）与 512 MiB 解压 / 校验
fqc --memory-limit 1024 compress -i reads.fastq -o reads.fqc --streaming
fqc --memory-limit 512 decompress -i reads.fqc -o out.fastq
fqc --memory-limit 512 verify -i reads.fqc

5 安全与正确性：零 unsafe 与格式契约

保证机制
内存安全纯 Rust，unsafe_code = deny 零 unsafe；处理不可信测序输入时消除整类内存漏洞
归档完整性每块 xxHash64 + footer 全局校验和；EOF magic 校验
格式兼容冻结 fixture（tests/fixtures/indexed-v2/）：审计基线生成 + manifest，未来 reader 必须能解压并逐字节一致
格式契约format_contract 测试锁定字节布局；跨族 magic 拒绝测试
解码防护块索引/偏移/流范围越界、读段数不符、footer 偏移越界均被严格拒绝
工程门禁cargo clippy -D warnings · ~190 单元/集成测试 · Criterion 基准回归 · 单静态二进制（仅依赖 libc）

6 性能现状与证据边界

fqc 的领域增益来自"块索引 + 组件级编码 + 读长自适应"的组合。以下数字如实标注证据范围，不把未验证的宣称当结论：

指标数值证据范围
压缩比（Archive）2.39×微型夹具（20 条 150bp 读，2231 字节）实测；大文件未验证
压缩/解压吞吐—未在生产规模复测（文档明确声明）
随机访问 / 范围解压O(log N)已实现的格式能力（非外推性能数字）
与 DSRC 2 / Leon 对比有潜力接近尚未被大型数据集证实
诚实的技术债声明（引自项目文档）："fqc 与 DSRC 2 / Leon 的压缩比竞争尚未被大型数据集证实；已证实的是格式能力（info / verify / 范围解压）和当前微型夹具上的 2.39×。下一步应先补证据，而不是根据未验证表格加功能。"——当前性能路线图的推进方向正是测量热点，而非新编解码器或大规模重写。
