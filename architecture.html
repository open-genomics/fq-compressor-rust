高性能架构设计

架构的核心命题：块。每个块是独立压缩的读段子集、块间零共享状态——这一个结构决定同时支撑多核并行、O(log N) 随机访问、范围解压与按块校验。

块 = 并行与随机访问的同一个答案

很多系统把"并行"和"随机访问"当成两个需要分别设计的问题。fqc 的洞见是：它们其实是同一个结构决定——块间零共享状态，既让多核各压各的互不干扰，也让索引能精确定位到任意一块。

独立压缩单元

块间无交叉引用 → 天然可并行，多核压缩/解压无锁争用。

O(log N) 随机访问

尾部索引按 block_id 二分定位，只解压目标块。

按块验证

verify --quick 基于归档结构操作，不必全量解码。

这是压缩比与随机访问张力的解法：块太小 → 索引开销大、ABC 无足够相似读段；块太大 → 随机访问粒度粗、内存峰值高。块大小即这个权衡的显式旋钮，是格式层最值得调优的参数。

三种执行模式：切换只关乎运维，不关乎格式

关键约束：三种模式产出完全相同的 .fqc 文件。因此模式是"这次压缩要多少内存、要多少压缩比"的运维决策，随时可换，归档不受影响。

Archive（默认）· 最佳压缩比

全量摄入 → 全局分析（长度分类 + 相似性分组）→ minimizer 重排 → 压缩。代价是内存高。适合生产归档、长期存储。

Streaming（--streaming）· 有界内存

单遍增量读取、流式压缩、增量写块，内存有界；放弃重排与全局分析。适合超大文件、内存受限环境。

Pipeline（--pipeline）· 多核吞吐

reader →[块缓冲]→ compressor →[块缓冲]→ writer 三阶段并发，在途缓冲最大化多核利用率。适合高吞吐生产流程。

内存预算：有界的资源承诺

--memory-limit 是全局参数，对 compress / decompress / verify 均生效。0 = 自动有限预算（约可用内存 75%），不是无限内存。

fail-fast，不留半成品

archive/pipeline 摄入超预算时，在创建 .fqc 前失败并提示改用 --streaming。

解码前先校验大小再分配

读取每个 header 先校验大小再分配，防御恶意/损坏归档。

代价提示

Pipeline 是分段执行路径，非严格低内存——要严格低内存请用 --streaming。

# 1 GiB 有界压缩（流式）与 512 MiB 解压 / 校验
fqc --memory-limit 1024 compress -i reads.fastq -o reads.fqc --streaming
fqc --memory-limit 512 decompress -i reads.fqc -o out.fastq
fqc --memory-limit 512 verify -i reads.fqc

安全与正确性：处理不可信输入的设计

零 unsafe

纯 Rust，unsafe_code = deny 编译期强制；处理不可信测序输入时消除整类内存漏洞。

归档完整性

每块 xxHash64 + footer 全局校验和；EOF magic 校验。

格式契约

format_contract 测试锁定字节布局；冻结 fixture 保证未来 reader 逐字节兼容；越界/偏移/读段数不符均被严格拒绝。

性能现状与证据边界

fqc 的领域增益来自"块索引 + 组件级编码 + 读长自适应"的组合。以下数字如实标注证据范围，不把未验证的宣称当结论：

指标数值证据范围
压缩比（Archive）2.39×微型夹具（20 条 150 bp 读，2231 B）实测；大文件未验证
压缩/解压吞吐—未在生产规模复测（文档明确声明）
随机访问 / 范围解压O(log N)已实现的格式能力（非外推性能数字）
与 DSRC 2 / Leon 对比有潜力接近尚未被大型数据集证实
诚实的技术债声明（引自项目文档）："与 DSRC 2 / Leon 的压缩比竞争尚未被大型数据集证实；已证实的是格式能力（info / verify / 范围解压）与微型夹具上的 2.39×。"当前性能路线图的推进方向是测量热点、补证据，而非新编解码器或大规模重写。
